# Second pass before done

Before declaring any substantive deliverable done, run one more pass against the request, not against your own work.

1. Re-read the original request and every correction, in order. For each one, point to the exact change that addresses it. A correction without a visible change is not done.
2. Read for what was not said: the requester's why. A deliverable can satisfy every stated correction and still miss why the work was asked for. If the why is not visible in the result, fix it or say so.
3. Find what is missing, not only what is wrong: which relevant method, evidence or check was available and not used. Record the findings even when the answer is none.
4. Check the work against the methods it routed to, not only against the request. For each source method the task used (located via `knowledge/methodologies/method-sources.md` or `scripts/local/route.py`, read fresh), list the requirements that method makes of this specific deliverable and point to where the output meets each one. An unmet requirement is not done - meet it, or declare it unmet with the reason. If he asked for an initial scaffold, an unmet requirement that belongs to a later phase is declared as such, never silently filled with invented content. An index hit is not a read; the method's own text is the requirement source.
5. Run the logged failure classes before delivery. Check the output against the correction classes already caught (`routines/learnings.md` rules and dated corrections since): shallow research presented as depth, unsupported or overclaimed statements, misattributed instructions, private material in the wrong class or place, tests and fixtures that do not match their actual inputs, meta commentary in reader-facing copy. Fix what is found and record the findings. A correction caught in any of his harnesses becomes a candidate row here - the general lesson only, never private context from someone else's harness.
6. Check the durable records: what was logged, where the example or evidence lives, and whether the next run can find it. A result that cannot be found again is not preserved.
7. Report what the second pass found and changed, or that it found nothing. Never claim the pass without findings or an explicit clean statement.

A clean second pass means the request, the corrections, the why, the routed methods' requirements and the logged failure classes were re-checked and findings were recorded. It does not prove the work is good; that stays with his review.
